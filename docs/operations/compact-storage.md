# Tracker 存储减量与自动回收

Tracker 用增量活动状态、压缩快照和有界原始记录代替逐心跳永久重放。累计业务账本仍会随用户和交易增长；这次去掉的是重复活动、全量快照行和全零账务的放大。

## 写入与保留规则

- 全零流量仍校验策略、维护会话基线、活动和完成事件，但不生成全零流量结算、分段、outbox 或日汇总。非零流量继续逐区间按原策略舍入后累计，不合并后计费。
- 已完成消息和任务默认保留 3 小时，会话及普通明细默认 12 小时。原始区间至少保留 48 小时，配置更长的明细期仍有效；异常诊断至少 30 天。未发布、未结算和未代表的依赖会延长保留。
- 原始活动回收前，流量、限速、H&R 和做种证据必须已消费或有持久增量状态。删除与回收任务在同一事务提交，失败整体回滚，暂时不能清理的记录 5 分钟后重试。
- 流量与原始记录均按持久游标有界扫描。尚未闭合的纯做种区间不生成逐心跳等待任务；每小时一个范围任务让以后满足条件的记录仍可被发现。
- 现有 storage-maintenance 服务持续分批回收，不需要每日全表删除。 历史游标通过带内层 LIMIT 的 LATERAL 查询直接定位索引起点；已领取的 raw 清理批次限定使用通用计划，避免 H&R 保护函数因首条旧记录而缓存时间索引扫描。DELETE 释放的空间首先由 PostgreSQL 复用，不能按删除行数声称操作系统已释放同样空间。

## 做种活动与证据

每条 announce 消费流注册不可变的激活整点和最大可信区间。激活点严格晚于注册时刻及已采集事件的小时，避免半个小时已有数据没有累计。采集事务内的数据库触发器按用户、种子和小时累计精确的活动区间并集、原始上传、来源数、最大序号及来源哈希链。

新小时使用内部 seeding.evidence.v3，将规范化区间、来源承诺和最终统计封入不可变证据。前 3 个非空小时逐项与原 v2 原始记录计算比较；时长、上传、首末时间、来源数或哈希链不一致就停止，不能放宽误差后通过。通过后停止重复扫描这些小时的所有心跳；已被验证的增量状态也能代表缺少快照的小时，原始记录仍须经过 48 小时及其他依赖检查。

原 v1/v2 证据保持原格式。对 Core 的 settlement.seeding.evidence.v1 消息保持兼容，Core 接收同样的时长、上传和快照计数；内部证据摘要版本改变，不把 v3 摘要伪装成旧摘要。跨小时上传及陈旧区间处理遵循现有 v2 规则。

## H&R 增量进度

每个义务保存源序号游标、封顶后的活动区间并集、非零上传发生点和最后证据时间。首次从原始记录建立状态并与旧 Evaluate 计算比较，以后只读取新序号。状态、义务变化和 outbox 在同一事务更新；清理旧心跳后重启仍继续累计。

保留非零上传点是为了准确复现迟到数据下首次满足分享率的时间，不能只存一个总字节数。V1 从仍被原始记录引用的 inbox 读取来源坐标，V2 直接读取 raw 上的坐标；确实缺少来源序号的旧记录继续走旧重放路径并保护原始记录。仍在跟踪的义务只有在所有相关增量游标覆盖记录后才释放原始依赖；未处理的完成事件也会保护后续活动。

## 全量 Swarm 快照

新投影器把每个 canonical chunk 存为 gzip，保留原始长度和 SHA256，不再为 chunk 中每个种子重复插入 SQL 行。单个解压结果受 512 KiB 合约上限约束；读取验证长度、摘要、来源、路由、快照序号、chunk 信息及跨 chunk 种子重复。升级中的旧行与新 chunk 可并存读取。

12 小时后回收有前后完整帧的冗余中间帧，每小时首末帧、整点、路由和消费流首帧、当前恢复帧及异常所需证据继续保护。已完成窗口的普通选中快照明细到期后可回收，永久证据仍保存最终计数及摘要。压缩 payload 每批最多 128 个，其他清理也都有批次上限。 旧行格式中仍受历史缺口保护的选中快照会跳过清理；新投影不再增加这些旧行，其他候选继续回收。

## 覆盖缺口与对账

持久扫描游标遇到缺少 fence 的小时，登记独立重试后继续后面的完整小时。没有把缺失小时写成零奖励，也没有扩大生产允许的快照延迟。删除原始数据按每条区间的实际覆盖检查，不能用最大的已完成小时掩盖之前的缺口；旧元数据保护使用连续闭合水位。

如果较早小时后来修复、同流更晚小时已经发布，修复结果进入 settlement.seeding_reconciliation_work，不自动倒序发放奖励。迟到来源也登记该队列；未解决对账保护活动、来源、快照与异常证据。状态变更追加不可变历史。旧 Core 的 v1 compensation preview 只能处理 v1，不应把 v3 强行送入该工具；v3 对账必须从封存的区间和来源承诺按明确的补偿方案处理，记录外部结算引用后再解决队列，不能为节省空间直接标记已解决。

容量监控同时显示连续闭合水位、最大已完成小时、缺口数量与最老小时、待对账数量、增量校验进度。即使后续小时追上当前，也会继续提示历史缺口。

## 发布与验证

迁移按顺序执行 202610160001_tracker_compact_storage.sql 、202610160002_tracker_incremental_activity.sql 和 202610160003_tracker_legacy_activity_coordinates.sql。Settlement 与 Core preflight 预期版本必须同步。sqlc 固定 v1.31.1，生成物需提交且重复生成一致。

在完整迁移的可丢弃数据库验证，绝不使用生产库运行测试：

    cd services/settlement
    GOWORK=off go test ./...
    PEERGO_TEST_TRACKER_DATABASE_URL=postgres://.../disposable_tracker \
    PEERGO_TEST_NATS_URL=nats://disposable-nats:4222 \
    GOWORK=off go test -race -count=1 ./internal/seedingevidence

ingest、settler、hnr、seedingevidence、storagecleanup 分别使用独立数据库。另验证 Core preflight 与做种奖励消费兼容。重点检查随机迟到/重复活动与旧算法一致、事务回滚、清理后重启、跨小时重叠、历史缺口隔离、压缩破损与边界保护。

发布前在服务器保存可恢复备份，协调迁移和依赖版本的服务。迁移在数据压缩和回收后不能安全 Down；故意拒绝向下回滚，恢复用备份或向前修复。上线后激活点及 3 个非空小时校验需要真实时间，校验完成前不会提前启用原始数据减量。历史大表不会因新版本上线立刻缩小；先追平有证据的清理，再评估物理重整的锁与临时空间。


## 旧行格式快照的一次性物理缩容

新投影器已经停止向 `ledger.seeding_swarm_snapshot_entries` 写入逐种子明细。历史表可能仍有数亿行；常规分批 DELETE 会产生大量 WAL，且不能立即缩小文件。`scripts/storage/snapshot-compact-prepare.sql` 和 `snapshot-compact-apply.sql` 用于经过单独授权的维护窗口，不加入日常定时任务。

这两个脚本只淘汰超过 12 小时、且现有 `ledger.is_redundant_hourly_snapshot` 返回 true 的完整中间帧。保留所有其他帧的当前记录，包括小时首末帧、整点、各路由和各消费流的首帧、已被窗口引用的帧及异常所需证据；未完成帧和新帧也保留。原始 announce、账本、奖励、H&R、压缩 payload、备份及 Docker 卷均不属于这个工具的淘汰范围。

操作前必须暂停所有旧表写入及后台清理；当前单机部署暂停 `peergo-worker`，保持 API 和旧站运行。评估 NATS 的磁盘余量和消息保留期。准备阶段锁定元数据及原表写入，登记全部帧、复制必须保留的行，并以每帧的有序 info hash、seeders 和 leechers 计算 SHA-256 和行数。目标表没有传入外键时才能执行。

准备完成后，将整个 `storage_snapshot_rewrite` schema 在原服务器备份为 custom archive；在隔离 PostgreSQL 中完整恢复，重新计算每一帧的数量和 SHA-256，与 manifest 全部匹配后才能将生产 control 的 `backup_verified` 标记为 true。记录备份文件 SHA-256、恢复结果和保留行数；不能仅用 TOC 校验代替恢复。运行前明确授权的范围需包括生产表的事务性 TRUNCATE/恢复及后台暂停。

应用阶段重新锁定相关元数据及原表，重新验证冗余条件、源数据和副本的逐帧摘要、计划与 manifest 的完整性以及没有新的旧格式帧。随后在一个事务内 TRUNCATE 原表、插回保留记录、再次逐帧验证，并登记已淘汰帧的清理进度。任一步失败均回滚。原表 OID 不变，原有 owner、授权、约束、索引和保护触发器不替换、不禁用；维护编排还应比较执行前后的完整 schema 定义。提交后 ANALYZE，恢复 worker，检查组件就绪、采集追赶及网站 HTTP。

隔离验证使用完整迁移后的空模板库：

```sh
python3 scripts/storage/test_snapshot_compaction.py \
  --container peergo-storage-rewrite-test-20261016 \
  --template rewrite_test_template
```

测试覆盖完整保留及原保护触发器、TRUNCATE 后故意报错的事务回滚、副本损坏、新旧格式记录出现、保留源数据变化、消费流首帧保护变化、未完成备份恢复验证的拒绝执行。测试容器必须隔离；不要对业务库运行测试夹具。

保留副本只作为本次维护的暂存数据。应用成功、服务恢复和备份恢复验证全部完成后可回收暂存行，保留压缩备份及 manifest。这个一次性重写不改变常规保留语义，也不替代原始记录的依赖检查和历史结算追赶。
